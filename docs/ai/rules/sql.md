# SQL 규칙

<!-- 이 문서의 역할: SQL·쿼리 파일·저장 프로시저 등 DB 쿼리 작성 규칙이다. -->

## 1. 기본 규칙

| ID | 규칙 | 이유 |
|----|------|------|
| SQL-001 | 값은 2장 "바인딩 방법"으로만 전달한다. 문자열을 이어 붙여 SQL을 만들지 않는다 | 문자열 연결은 SQL 인젝션의 직접 원인이다 |
| SQL-002 | 정렬 컬럼·테이블명처럼 바인딩할 수 없는 값은 코드에 정의한 허용 목록에서 고른 값만 넣는다 | 허용 목록 없이 넣으면 SQL-001과 같은 인젝션이 생긴다 |
| SQL-003 | UPDATE·DELETE에는 WHERE 조건을 반드시 쓴다. 테이블 전체를 대상으로 하는 문장이 필요하면 작성 전에 사람에게 묻는다 | 조건 누락은 전체 데이터 변경 사고로 이어진다 |
| SQL-004 | `SELECT *`를 쓰지 않는다. 필요한 컬럼을 나열한다 | 컬럼 추가 시 결과 매핑이 깨지고 불필요한 데이터를 읽는다 |
| SQL-005 | 목록 조회 쿼리에는 페이징 또는 최대 건수 제한을 둔다 | 데이터가 늘면 메모리 부족과 응답 지연이 생긴다 |
| SQL-006 | WHERE 조건의 컬럼에 함수나 형변환을 씌우지 않는다. 예: 날짜 컬럼을 문자열로 바꿔 비교하지 않고 `컬럼 >= 시작값 AND 컬럼 < 종료값` 범위 조건으로 쓴다 | 컬럼을 가공하면 인덱스를 쓰지 못한다 |
| SQL-007 | 테이블·컬럼명은 domain.md "주요 테이블", 스키마 문서, 기존 쿼리 중 하나에서 확인한 이름만 쓴다 | 추측한 이름은 실행 오류가 되거나 다른 컬럼을 건드린다 |
| SQL-008 | DDL은 2장 "DDL 스크립트 위치"(schema.sql)에만 쓴다. Python 코드 안에 DDL 문자열을 쓰지 않는다 (BAN-003) | 테이블 구조를 한 파일에서 확인할 수 있어야 한다 |

## 2. 이 프로젝트의 DB 정보

| 항목 | 값 |
|------|----|
| 스키마/계정 | 해당 없음(SQLite 파일 `backend/data/fixlog_automation.db`, 계정 없음) |
| 바인딩 방법 | sqlite3 `?` 또는 `:이름` 파라미터. f-string에는 코드 상수(컬럼 목록)와 조건 조각만 넣는다 |
| 테이블 이름 규칙 | 소문자 스네이크, 복수형 |
| 컬럼 이름 규칙 | 소문자 스네이크 |
| 공통 컬럼 | `created_at` |
| 날짜 저장 형식 | TEXT, UTC ISO 8601(밀리초) `2026-11-04T02:14:09.123+00:00` |
| 채번 방식 | `uuid4().hex`(batches, runs), `custom-` + uuid 8자리(custom_scenarios), AUTOINCREMENT(run_steps) |
| 페이징 방식 | `LIMIT ? OFFSET ?` |
| 쿼리 파일 위치 | `backend/app/repository.py`(쿼리 문자열), `backend/app/schema.sql`(스키마) |
| 쿼리 ID 이름 규칙 | repository 함수명 `select·insert·update·delete` + 대상 |
| DDL 스크립트 위치 | `backend/app/schema.sql` |
