## 1. 작업 순서

| 단계 | 할 일 | 끝난 상태 |
|------|------|----------|
| 1. 이해 | 요청 메시지 또는 `docs/specs/` 명세 파일을 읽는다. AGENTS.md 문서 지도에서 해당 문서를 읽는다 | 대상 화면·기능·데이터가 특정됨 |
| 2. 조사 | 관련 코드를 검색하고 architecture.md의 예시 파일과 대표 요청 흐름을 확인한다 | 수정·생성할 파일 목록이 나옴 |
| 3. 정리·계획 | 큰 작업(WF-009)이면 명세 초안(1~4장 요구, 5장 구현 계획)을 쓰고 "개발 시작"을 기다린다. 작은 작업이면 목적·대상·완료 기준을 한 줄씩 정리해 보여 주고, 2장 조건에 해당할 때만 계획을 보고하고 승인을 기다린다 | 명세 "확정" 또는 3줄 정리·승인 완료 |
| 4. 구현 | 규칙 문서와 명세 5장 계획에 따라 수정한다 | 파일 목록대로 수정 완료 |
| 5. 검증 | 3장 순서로 검증한다 | 검증 결과 확보 |
| 6. 보고 | 4장 형식으로 보고한다. 명세 파일이 있으면 같은 내용을 명세 6장 "결과"에 쓴다. 사람의 확인 후 다시 고치면 6장에 덧붙인다 | 보고 완료 |

## 2. 멈추고 사람에게 묻는 조건

| ID | 조건 | 이유 |
|----|------|------|
| WF-001 | 요청과 코드 조사로 정할 수 없는 내용이 있다. 큰 작업은 추측해 채우지 않고 명세 "4. 미결 사항"에 질문으로 쓴다. 작은 작업은 대상이나 완료 기준을 정할 수 없을 때 묻는다 | 추측으로 만든 결과는 다시 만들어야 한다 |
| WF-002 | 요청 내용과 기존 코드의 동작이 서로 다르다 | 어느 쪽이 맞는지는 업무 담당자만 안다 |
| WF-003 | 수정 파일이 5개를 넘거나 project.md "공통 모듈"을 수정해야 한다. 수정 전에 계획을 보고하고 승인을 받는다. 명세 파일이 있으면 5장 구현 계획에 쓰고 "개발 시작"을 승인으로 본다 | 영향 범위가 커서 사전 검토가 필요하다 |
| WF-004 | `backend/app/schema.sql`의 테이블·컬럼·인덱스를 추가·변경·삭제해야 한다 (BAN-003) | 기존 로컬 실행 기록 DB와 호환이 깨질 수 있다 |
| WF-005 | 파일을 삭제하거나 이름을 바꿔야 한다. 명세 5.1에 쓰고 "개발 시작"을 받았으면 다시 묻지 않는다 | 다른 곳에서 참조하고 있을 수 있다 |
| WF-007 | 같은 오류를 2번 고쳐도 해결되지 않는다. 3번째 시도 전에 시도한 내용과 결과를 보고한다 | 같은 방향의 반복 시도는 코드만 망가뜨린다 |
| WF-008 | 명세 파일의 상태가 "확정"이 아니거나 "미결 사항"에 해결되지 않은 질문이 남아 있다. "가정: A로 진행(담당자 결정)"으로 쓴 항목은 해결된 것으로 본다 | 정해지지 않은 내용으로 만든 코드는 다시 만들어야 한다 |
| WF-009 | 큰 작업(신규 화면·API·배치, 테이블·컬럼 변경(WF-004), 수정 파일 수 기준 초과(WF-003) 중 하나)인데 `docs/specs/`에 명세 파일이 없다. 요청과 코드 조사로 템플릿 초안을 "작성중" 상태로 만들고 확인을 요청한다 | 큰 작업은 결정 내용이 파일로 남아야 리뷰와 인수인계에 쓸 수 있다 |
| WF-016 | 명세 상태를 바꾸거나 확정된 명세의 1~5장을 고쳐야 한다. 사람이 명시적으로 지시했을 때만 한다("개발 시작" → 확정, "완료" → 완료). 확정 뒤 지시 없이 AI가 쓰는 곳은 6장 "결과"뿐이다 | 사람이 확인한 내용만 개발 기준이 되어야 한다 |

## 3. 검증

### 3.1 검증 순서

아래 순서대로 진행한다. 각 단계의 "조건"에 해당하지 않으면 건너뛰고 보고에 건너뛴 이유를 쓴다.

| ID | 검증 | 조건 | 이유 |
|----|------|------|------|
| WF-010 | AGENTS.md "빌드" 명령을 실행해 성공을 확인한다 | 모든 변경 | 컴파일 오류는 다른 검증보다 먼저 걸러야 한다 |
| WF-011 | AGENTS.md "자동 테스트" 명령으로 변경한 모듈의 테스트를 실행한다 | 자동 테스트 명령이 "없음"이 아닐 때 | 기존 기능이 깨졌는지 사람 손 없이 확인할 수 있다 |
| WF-012 | AGENTS.md "로컬 실행" 명령으로 실행하고 변경한 화면·API·배치를 호출해 응답과 결과 데이터를 확인한다 | 로컬에서 실행할 수 있을 때 | 빌드가 성공해도 실행 중 오류(SQL 오류, 매핑 오류, 화면 스크립트 오류)는 남는다 |
| WF-013 | 사람이 따라 할 수동 확인 절차(화면 경로, 입력값, 기대 결과, 확인할 테이블·데이터)를 보고에 쓴다 | WF-011과 WF-012를 둘 다 하지 못했을 때 | 검증을 사람에게 넘기려면 같은 절차로 재현할 수 있어야 한다 |
| WF-014 | 실행하지 않은 검증을 "확인 완료"로 보고하지 않는다. 실행한 검증과 실행하지 못한 검증을 나눠 쓴다 | 모든 보고 | 검증되지 않은 변경이 검증된 것으로 배포된다 |

### 3.2 검증 환경

| 항목 | 값 |
|------|----|
| 로컬 접속 주소 | http://127.0.0.1:8000 (API + 빌드된 대시보드), 대시보드 개발 서버 http://localhost:5173 |
| 테스트 계정 | 담당자 소유 Google 계정. 이메일·비밀번호는 저장소 최상위 `.env`, 로그인 상태는 `backend/.auth/state.json`(둘 다 git 제외, BAN-104) |
| 검증에 쓰는 DB | 로컬 SQLite `backend/data/fixlog_automation.db`(이 프로그램 전용). 자동 테스트는 임시 폴더의 DB를 쓴다 |
| 자동 테스트 코드 위치 | `backend/tests` (가짜 FixLog 화면: `backend/tests/fixture_site/index.html`) |

## 4. 완료 보고 형식

```markdown
## 변경 요약
- 무엇을, 왜 바꿨는지 1~3줄

## 변경 파일
- `경로` : 변경 내용 한 줄

## 검증
- 빌드: 실행한 명령과 결과
- 자동 테스트: 실행한 명령과 결과, 또는 건너뛴 이유
- 실행 확인: 호출한 화면·요청과 결과, 또는 건너뛴 이유
- 수동 확인 절차: WF-013에 해당하면 화면 경로, 입력값, 기대 결과, 확인할 데이터

## 완료 기준 결과
- 명세 3장 번호별로 통과 / 실패 / 미확인과 그 근거

## 명세와 달라진 점
- 사람과 상의해 바꾼 것, 조사 결과 명세대로 할 수 없었던 것과 그 이유. 없으면 "없음"

## 확인 필요
- 사람이 결정하거나 확인해야 할 것. 없으면 "없음"
```
