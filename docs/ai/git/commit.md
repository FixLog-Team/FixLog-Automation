# 커밋 규칙

<!-- 이 문서의 역할: 커밋 메시지 형식과 커밋을 나누는 기준이다. 사람과 AI(commit-generate 스킬 포함)가 모두 따른다. -->
<!-- 1장 설정은 담당자가 정한다(2026-11-04). -->

## 1. 설정

| 항목 | 값 |
|------|----|
| AI 커밋 | 허용 (push는 PR 스킬로만, BAN-007) |

## 2. 원칙

| ID | 규칙 | 이유 |
|----|------|------|
| GIT-010 | 커밋 하나에는 목적 하나만 담는다. 성격이 다른 변경(기능 + 리팩터링, 코드 + 의존성, 코드 + 문서)은 커밋을 나눈다 | 커밋 단위로 리뷰하고 되돌릴 수 있다 |
| GIT-011 | 요약에는 구현 방법이 아니라 바뀐 결과와 의도를 쓴다 | 로그만 보고 무엇이 바뀌었는지 알 수 있다 |
| GIT-012 | 동작이 바뀌면 `feat`·`fix`, 동작이 100% 같으면 `refactor`를 쓴다. 버그를 고쳤으면 `refactor`로 쓰지 않는다 | 동작 변경이 리팩터링으로 숨으면 장애 원인을 찾을 수 없다 |
| GIT-013 | 같은 기능의 파일(화면 + 서버 코드 + 쿼리)은 한 커밋으로 묶는다 | 반쪽짜리 커밋은 빌드가 깨지거나 되돌릴 때 짝이 맞지 않는다 |

## 3. 메시지 형식

```text
[type] [작업ID] 요약

본문 (선택)
```

- 요약: 50자 이내, 마침표 없음
- 작업ID: 브랜치 이름에 SPEC ID가 있으면 쓴다. 없으면 `[작업ID]`를 통째로 뺀다 (branch.md 2장)
- 본문: 요약만으로 이유를 알 수 없을 때 한 줄 띄고 쓴다

| type | 쓰는 경우 |
|------|----------|
| `feat` | 사용자 관점의 기능 추가·변경 |
| `fix` | 버그 수정 |
| `refactor` | 동작 변경 없는 구조·이름 개선 |
| `docs` | 문서만 수정 |
| `chore` | 빌드, 설정, 의존성, 스크립트 |
| `hotfix` | 배포 후 긴급 수정 |

## 4. 예시

```text
[feat] [SPEC-20261104-document-write-scenario] 문서 작성·삭제 시나리오 추가
[fix] 삭제 후 목록 확인을 새로고침 뒤 검색으로 변경
[refactor] 단계 선행 조건을 StepDefinition.requires로 이동
[chore] 기본 실행 시간 제한 180초로 변경
```

쓰지 않는 메시지:

```text
[fix] 수정
[refactor] 정리
[feat] 여러 가지 수정
```
