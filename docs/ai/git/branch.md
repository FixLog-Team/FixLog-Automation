## 1. 설정

| 항목 | 값 |
|------|----|
| 배포 브랜치 | main |
| 통합 브랜치 | 없음 |
| PR 기준 브랜치 | main |
| 직접 push 금지 브랜치 | main (최초 커밋 push 1회는 담당자 지시로 예외) |

## 2. 브랜치 종류

| 브랜치 | 역할 | 이름 |
|--------|------|------|
| 배포 브랜치 | 배포 기준. 검증을 마친 변경만 머지한다 | 1장 설정값 |
| 통합 브랜치 | 개발 중인 최신 상태. 완료된 작업 브랜치를 머지한다 | 1장 설정값 |
| 작업 브랜치 | 작업 하나의 변경만 담는다 | `{유형}/{작업ID 또는 영문 설명}` |

- 유형: `feature`(기능), `fix`(버그), `refactor`, `docs`, `chore`, `hotfix`(배포 후 긴급 수정)
- 작업ID: 명세 파일이 있으면 SPEC ID를 쓴다. 예: `feature/SPEC-20261104-document-write-scenario`
- 명세 파일이 없는 작은 작업: 영문 소문자와 하이픈으로 설명을 쓴다. 예: `fix/google-login-email-selector`

## 3. 규칙

| ID | 규칙 | 이유 |
|----|------|------|
| GIT-002 | 1장 "직접 push 금지 브랜치"에는 push하지 않는다. PR로만 머지한다 | 검토되지 않은 변경이 공유 브랜치에 들어간다 |
| GIT-003 | 작업 브랜치는 PR 기준 브랜치에서 만든다 | 기준이 다르면 PR에 관계없는 커밋이 섞인다 |
