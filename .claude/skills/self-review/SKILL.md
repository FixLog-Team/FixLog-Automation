# 셀프 리뷰

검사 기준은 이 파일에 쓰지 않는다. 프로젝트에 있는 규칙 문서를 읽고, 그 문서의 규칙 ID로 판정한다.

## 1. 검사 범위 수집

1. `docs/ai/git/branch.md`에서 "PR 기준 브랜치"를 읽는다. 문서가 없으면 사람에게 기준 브랜치를 묻는다.
2. 변경 파일을 모은다.
   - 커밋된 변경: `git diff {기준 브랜치}...HEAD --name-only`
   - 커밋하지 않은 변경: `git status --short`. 있으면 범위에 넣고 리포트 맨 위에 적는다.
3. 변경 파일과 diff를 모두 읽는다. 파일 목록만 보고 판단하지 않는다.
4. 브랜치 이름에서 `SPEC-[0-9]{8}-[a-z0-9-]+`를 찾는다. 있으면 `docs/specs/{SPEC ID}.md`를 읽는다.

## 2. 읽을 규칙 문서

`AGENTS.md` 4장 "문서 지도"를 따라 변경 파일 종류에 맞는 문서를 읽는다. 저장소에 없는 문서는 건너뛴다.

| 항상 읽는다 | 변경 파일에 따라 읽는다 |
|------------|----------------------|
| `AGENTS.md` 3장 금지사항(BAN) | 서버 코드 → `docs/ai/rules/backend.md`(BE) |
| `docs/ai/rules/common.md`(COM) | SQL·쿼리 파일 → `docs/ai/rules/sql.md`(SQL) |
| `docs/ai/rules/convention.md`(CONV, 이름 규칙·형식) | 화면 코드 → `docs/ai/rules/frontend.md`(FE) |
| `docs/ai/rules/project.md`(PRJ, 공통 모듈·수정 금지 영역) | 업무 용어·테이블 → `docs/ai/domain.md`(DOM) |
| `docs/ai/architecture.md`(ARC, 레이어별 위치·책임) | |

## 3. 검사

변경된 줄과 그 주변만 검사한다. 변경되지 않은 기존 코드의 위반은 적지 않는다(BAN-004).

| 구분 | 확인할 것 |
|------|----------|
| A. 금지사항 | BAN 위반. 비밀 정보, 범위 밖 수정, 승인 없는 라이브러리 변경 |
| B. 구조 | 새 파일 위치와 이름이 architecture.md "레이어별 위치"와 맞는가. 호출 방향(ARC-001·002), 같은 표의 "넣지 않는 것", 구조 원칙(ARC-101~) |
| C. 공통·컨벤션 | COM 규칙, convention.md 이름 규칙·형식·작성 규칙(CONV). 새 파일은 convention.md, 기존 파일은 그 파일의 스타일(COM-002) |
| D. 레이어별 규칙 | 읽은 BE·SQL·FE·PRJ·DOM 규칙 |
| E. 명세 | 명세가 있을 때만. 5.1 수정 파일과 실제 변경 파일이 같은가. 3장 완료 기준 중 코드로 확인할 수 있는 것이 구현되었는가. 6장 결과가 실제 변경과 맞는가 |

판정:
- ❌ 위반: 규칙 문장에 명확히 어긋난다. 규칙 ID를 반드시 적는다.
- ⚠️ 검토: 규칙에 어긋날 수 있지만 맥락을 사람이 판단해야 한다.
- 규칙 문서에 없는 개인 취향은 적지 않는다.
- 아직 구현하지 않은 자리(빈 메서드, TODO)는 판정하지 않는다.

## 4. 리포트

```markdown
# 셀프 리뷰 리포트

- 브랜치: {브랜치} (기준: {기준 브랜치})
- 커밋 수: N개 / 커밋하지 않은 변경: 있음·없음
- 명세: docs/specs/{SPEC ID}.md 또는 "없음"
- 읽은 규칙 문서: {목록}

## ❌ 위반
| 파일:줄 | 규칙 ID | 내용 | 고치는 방법 |
|--------|--------|------|-----------|

## ⚠️ 검토
| 파일:줄 | 규칙 ID | 내용 | 제안 |
|--------|--------|------|------|

## 명세 대조
- 5.1 계획에 없는 변경 파일: {목록 또는 "없음"}
- 5.1 계획에 있는데 변경되지 않은 파일: {목록 또는 "없음"}
- 3장 완료 기준: 번호별 구현 확인 / 코드로 확인 불가

## 결과
- ❌ N건, ⚠️ N건
```

- "고치는 방법"은 구체적으로 쓴다. 예: "steps.py:120 — asyncio.sleep(2)로 화면을 기다린다 → expect(...).to_be_visible()로 바꾼다 (PRJ-003)"
- ❌가 있으면 "수정 후 다시 실행하세요"라고 끝에 쓴다.
- 코드는 수정하지 않는다. 사람이 수정을 요청하면 그때 고친다.
